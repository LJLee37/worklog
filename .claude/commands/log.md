---
description: 오늘 날짜 파일에 이번 세션의 작업/AI 활용 내역을 요약해서 기록한다
---

이 저장소는 public이다. 시작하기 전에 `CLAUDE.md`의 "절대 규칙: 민감정보를
커밋하지 않는다" 섹션을 다시 확인한다.

> **확인 지점은 한 번뿐이다 — 파일에 쓰기 전.** 초안을 보여주고 승인받은 뒤에는
> pull → 수정 → 커밋 → push를 **중간 확인 없이 스스로 끝낸다.** 이 저장소에 한해
> "push는 매번 확인받는다"는 공용 지침보다 이 규칙이 우선한다.

1. 오늘 날짜(`YYYY-MM-DD`)를 확인하고, `<YYYY>/<YYYY-MM-DD>.md` 파일이 있으면
   **읽는다(아직 고치지 않는다).** 없으면 아래 템플릿을 기준으로 새로 쓸 준비를 한다:

   ```markdown
   # YYYY-MM-DD

   ## 작업
   -

   ## AI 활용
   -
   ```

2. 이번 세션(또는 사용자가 지금까지 이야기한 작업)을 되짚어 **초안을 만든다**
   (아직 파일에 쓰지 않는다):
   - **작업** 섹션에 실제로 한 일을 항목으로 정리한다 (AI 없이 한 일 포함).
   - **AI 활용** 섹션에 어떤 AI 도구/모델을 썼는지, 무엇을 위해 썼는지, 결과가
     어땠는지를 간단히 요약한다. 프롬프트 원문을 통째로 옮기지 말고 요지만
     남긴다.
   - 이미 그날 파일에 내용이 있으면 지우지 말고 이어서 추가한다.

3. **민감정보 점검**: 지금 추가하려는 내용에 비밀번호/토큰/API 키/SSH
   개인키/VPN·EAP 자격증명/실제 도메인이나 공인 IP/타인의 개인정보가 섞여
   있지 않은지 확인한다. 섞여 있다면 `<REDACTED>`로 바꾸거나 "무엇을 했는지"만
   남기는 문장으로 바꾼다.

4. **승인 요청 (유일한 확인 지점).** 파일에 쓰기 **전에** 추가할 내용을 그대로
   사용자에게 보여주고 허락을 받는다. 요약하거나 "이런 내용을 쓰겠다"고 말만 하지
   말고, 파일에 들어갈 문장을 그대로 보여준다. 수정 요청이 오면 고쳐서 다시 보여주고,
   승인이 떨어질 때까지 파일을 건드리지 않는다.

5. **승인 후에는 스스로 끝낸다 — 중간에 다시 묻지 않는다.** 순서:

   1. `git pull --rebase`로 원격을 먼저 반영한다(다른 기기에서 같은 날 파일을
      고쳤을 수 있다).
   2. 승인받은 내용을 파일에 쓴다. 그날 파일에 이미 내용이 있으면 **지우지 말고
      이어서** 추가한다. pull 결과 파일이 달라졌으면 그 위에 다시 얹는다.
   3. `git add` 후 `git diff --cached`를 실제로 읽어 민감정보를 다시 점검한다.
   4. 커밋한다. 메시지는 Conventional Commits + 한국어 설명 컨벤션.
   5. `git push`까지 진행한다.
   6. 끝나면 커밋 해시와 푸시 결과를 보고한다.

6. **충돌(conflict) 처리.** pull이나 push에서 충돌이 나면:

   - **해결할 수 있으면 해결하고 진행한 뒤, 무엇이 충돌했고 어떻게 합쳤는지
     보고한다.** 이 저장소의 충돌은 대개 같은 날 파일에 두 기기가 각각 항목을
     추가한 형태이므로, **양쪽을 모두 남기는 방향**이 기본이다 — 남의 기록을
     지워서 해결하지 않는다.
   - **스스로 판단이 서지 않으면 손대지 말고 먼저 보고하고 결정을 기다린다.**
     (같은 항목이 서로 다르게 서술돼 어느 쪽이 맞는지 모를 때, 파일 구조가
     어긋났을 때 등.)
   - `git push --force`, `git reset --hard`, 남의 커밋을 버리는 방식은 **어떤
     경우에도 스스로 하지 않는다.** 반드시 사용자에게 묻는다.
