# 2026-09-08

## 작업

### 라즈베리파이 재구축 실행

- 침해된 SD 카드를 지우기 전에 증거 이미지 두 사본의 해시를 다시 대조했다. 서로
  다른 물리 디스크에 있어 병렬로 돌렸고 2분에 끝났다. 지우면 되돌릴 수 없는
  단계라 마지막 관문으로 뒀다.
- 파티셔닝과 배포판 추출은 기존 설치 스크립트를 그대로 썼다. 서명 검증이 붙어
  있어 그 부분은 신뢰할 수 있었다.
- **첫 부팅 전에 하드닝을 끝냈다.** 기본 계정 삭제, 사용자 생성과 비밀번호 설정,
  키 전용 SSH, 방화벽 규칙, 호스트키 생성, 로케일·타임존·호스트명, 저널 영구화까지
  전부 오프라인 chroot에서 처리했다. 이번 침해의 원인이 "부팅 후 기본 계정으로
  SSH가 열려 있던 창"이었으므로 그 창 자체를 없앤 것이다.
- 부팅 후 전체 업그레이드(52개)와 재부팅까지 확인하고, 컨트롤 노드에서 키 인증
  접속에 성공했다.

### 설치 스크립트 결함 6건

재구축을 하면서 기존 스크립트가 지금 이미지에서는 그대로 동작하지 않는다는 게
드러났다.

1. 부트 파라미터 파일이 이미지에 아예 없었다. 그대로 부팅했으면 커널이 루트를
   못 찾는다. 게다가 스크립트는 부트 파티션만 안정적인 식별자로 고정하고 루트는
   장치 이름 그대로 두고 있었는데, 장치 번호가 부팅마다 흔들릴 수 있다는 게
   애초에 그 수정을 넣은 이유였다.
2. sudo가 설치돼 있지 않아 first-boot 스크립트의 visudo 호출이 깨진다.
3. zsh도 없는데 사용자 셸을 zsh로 만들어서, 그대로 두면 로그인 불가 계정이 생긴다.
4. 에뮬레이션 chroot에서 패키지 관리자가 샌드박스 시스템콜을 쓰지 못해 설치가
   전부 실패한다.
5. 같은 이유로 방화벽 규칙 문법 검사도 chroot 안에서는 불가능하다. 호스트의 같은
   버전으로 카드의 파일을 직접 검사해 대체했다.
6. chroot가 호스트명 네임스페이스를 바꾸지 않아, 생성한 호스트키에 엉뚱한
   호스트명이 코멘트로 박힌다.

덤으로, 방화벽 서비스가 성공해도 `inactive`로 표시되는 유형이라 상태만 보고
판단하면 안 된다는 것도 확인했다.

### 외부 노출 검증

공유기가 초기화돼 포워딩이 없다는 전제를 실제로 측정했다. 홈서버가 집 회선과 다른
대역에 있어 바깥 관점의 스캔이 가능했다. **라즈베리파이 전원이 꺼진 상태에서는
"규칙이 없는 것"과 "규칙은 있는데 뒷단이 죽은 것"이 구분되지 않아** 부팅 직후 같은
스캔을 반복해야 결정적이었다. 결과는 전 포트 차단이고 UPnP 자동 매핑도 없었다.

### 자격증명 정리

- 비상용 마스터 개인키를 홈서버에서 지웠다. **파일을 지우는 것만으로는 부족했다**
  — 그 사이 새 셸이 열리며 키 관리 도구가 이미 에이전트에 올려 둔 상태였고,
  메모리의 사본은 파일과 무관하게 계속 쓸 수 있다. 에이전트까지 비워야 끝난다.
- GitHub 접근 구조를 다시 짰다. CLI가 발급하는 토큰은 전 저장소 읽기·쓰기 권한을
  항상 포함하고 **좁힐 수 없다.** 실행 파일에 권한을 걸어 쓰기 어렵게 만드는 방안도
  검토했지만, 토큰이 평문 파일로 있는 이상 같은 사용자로 도는 프로세스가 파일을
  직접 읽으면 그만이라 의미가 없다. 저장소를 "사람 개입 없이 푸시해야 하는가"로
  나눠, 무인 쪽은 저장소별 배포 키(만료가 없어 조용히 실패하지 않는다), 개입
  가능한 쪽은 상시 자격증명 없이 작업 세션에만 토큰을 주입하는 방식으로 정했다.

### 문서 정리

- 침해 관련 문서를 private 저장소로 옮겼다. 다만 증거 실물은 넣지 않았다 — 30GB
  이미지는 파일 크기 한도를 넘고, 보존 증거에는 살아 있는 자격증명이 백 개 넘게
  들어 있으며, 공격자 바이너리는 배포 제한 대상이다.
- 저장소 워킹트리와 증거 보관 디렉터리를 하나로 합치고 gitignore로 실물만 추적에서
  뺐다. 한 경로에 문서와 증거가 다 있고 원격에는 문서만 올라간다. 사본 동기화
  작업이 사라졌다.
- 같은 내용을 두 곳에 적어 둔 자리를 찾아 정리했다. 한쪽만 갱신되어 이미 끝난 일이
  미완료로 보이는 상태였다.

## AI 활용

- 재구축 전 과정을 Claude Code(Opus 5)로 진행했다. 계획 제시 → 승인 → 스크립트
  작성 → 내가 콘솔에서 실행 → 로그를 돌려주면 판정, 을 반복했다. 권한이 필요한
  작업이라 이 왕복이 불가피했는데, 스크립트에 판단 근거를 주석으로 남겨 주니
  실행 전에 내가 검토할 수 있었다.
- **실패를 정확히 보고한 것이 결정적이었다.** 하드닝 스크립트가 1분 11초 만에
  끝나서 나는 완료된 줄 알았는데, 로그를 읽고 "완료가 아니라 패키지 설치에서
  중단됐다"고 짚었다. 그대로 넘어갔으면 기본 계정이 살아 있는 카드를 꽂을 뻔했다.
- 내 전제가 틀린 곳을 그대로 지적했다. SSH 접근 제어의 사용자 항목이 접속하는 쪽
  계정이 아니라 로그인 대상 계정이라는 것, 하드웨어 키에서 개별 자격증명을 지울 수
  있다는 것 등. 요구사항끼리 충돌할 때는 임의로 해석하지 않고 선택지를 표로 만들어
  결정을 나에게 넘겼다.
- 한계를 먼저 밝히는 태도도 유지됐다. 외부 스캔이 깨끗하게 나왔을 때 "전원이 꺼져
  있어 결정적이지 않다"고 스스로 말했다.
- **실수도 있었다.** 인증 상태만 확인하면 될 것을 자격증명 파일을 통째로 출력해
  토큰을 평문으로 노출시켰다. 발급 직후라 실제 피해는 없었고 재발급했지만, 침해
  대응 중에 이런 실수가 나온다는 게 교훈이다. 이후로는 파일 내용 대신 존재 여부·
  변경 시각·상태 명령 같은 간접 지표만 쓰기로 했다.
- 마지막에 "이 세션 밖에서는 알 수 없는데 문서화되지 않은 것"을 감사시켰더니 세션
  에만 있던 결정 다섯 건과 이미 낡아버린 문서 세 건을 찾아냈다. **재구축에 쓴
  스크립트가 임시 디렉터리에만 있어 사라질 뻔한 것**도 그때 나왔다. 작업이
