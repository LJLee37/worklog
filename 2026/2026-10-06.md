# 2026-10-06

## 작업

- 메인 서버의 CPU 팬과 케이스 팬 속도를 리눅스에서 읽고 제어할 수 있게 했다. 메인보드 센서 칩 드라이버를 올려 팬 속도와 PWM 출력을 확인했고, BIOS 가 두 팬 모두 CPU 온도만 보고 돌려 하드 디스크 온도는 반영하지 않는다는 것을 찾았다.
- 팬을 직접 보거나 들을 수 없어, PWM 출력을 하나씩 12분 동안 최대로 올리며 팬 속도와 디스크 온도를 기록하는 시험 스크립트로 어느 출력이 케이스 팬인지 가렸다. 케이스 팬을 최대로 올리자 NAS 디스크 둘이 12분 만에 3~4도 내려갔다.
- 최근 디스크 온도가 45도를 넘던 원인이 이번 달 처음 돈 btrfs scrub(디스크 전체를 읽어 체크섬을 확인하는 월간 점검)이라는 것을 찾았다. 평소 온도는 37~40도였고, 팬 시험도 scrub 도중이라 가장 부하가 큰 상황의 효과를 잰 셈이 됐다.
- 케이스 팬을 디스크 온도와 CPU 온도로 돌리는 데몬과 명령을 Ansible role 로 만들었다. 평소에는 지금처럼 조용히 돌고 디스크가 41도를 넘을 때만 올라간다. 개인 비서는 sudo 없이 정해진 범위와 시간 안에서만 속도를 잠시 바꿔 달라고 요청할 수 있고, 데몬이 어떻게 끝나든 팬은 BIOS 자동 제어로 돌아간다. 비서용 스킬도 더했다.
- 가짜 센서 트리로 데몬과 명령을 시험하는 스크립트를 만들어 104개 항목을 확인했고, systemd 유닛으로 강제 종료와 watchdog 시간 초과 뒤에도 팬이 BIOS 자동으로 돌아오는지 실측했다.
- 디스크 수명을 위해 쉴 때 회전을 멈추는 방안을 검토했다. 디스크는 이미 쉴 때 헤드를 걷어 올리고 있고, 회전 정지는 수명 이득이 불분명해 보류했다.
- 변경은 서명 커밋과 적용을 위해 컨트롤 노드 세션에 패치와 인계 문서로 넘겼다(아직 적용 전).
- 같은 날 새벽 컨트롤 노드에서 서명 커밋과 적용을 마쳤다. 적용 뒤 팬이 최대일 때 같은 설정을 매번 다시 쓰던 작은 문제를 실제 칩에서 찾아 고쳤고, 시험 항목을 더해 다시 적용했다.

## AI 활용

- Claude Code(Opus 5.5)로 진행했다. 센서 칩 확인, 시험 설계, 로그 분석, role 과 시험 작성, 인계까지 한 세션에서 했고, 컨트롤 노드의 다른 Claude Code 세션과 원격 제어 메시지로 패치 전달 방식과 확인 항목을 맞췄다.
- 좋았던 점: 팬을 볼 수 없다는 제약에서 디스크 온도 반응으로 팬을 가리는 시험을 제안했다. 그 결과를 기존 디스크 온도 기록과 비교해 scrub 이 원인임을 찾았고, 그에 맞춰 곡선을 다시 물어 평소 소음을 늘리지 않는 쪽으로 정했다.
- 아쉬웠던 점: scrub 중의 측정값을 평소 값으로 읽어 "평소에도 팬이 거의 최대로 돌 것"이라고 잘못 말했다가 바로잡았다. 시험 스크립트의 조건식 우선순위 실수로 systemd 시험이 한 번 건너뛰어졌고, 확인용 명령의 리다이렉션 실수로 홈에 작은 파일 넷이 생겨 옮겨 두었다. 저장소 사본이 오래돼 비서 모델을 옛 값으로 말한 적도 있다.
- 본인이 먼저 짚은 것: 케이스 팬 네 개가 허브 하나로 묶여 있다는 배치, 저소음 팬이라 소음은 감수할 만하다는 판단, 디스크 회전 정지보다 수명을 우선한다는 기준.

## 작업

- 장부 작업 세션이 반복 일정을 표준 반복 규칙(휴대폰 캘린더와 같은 형식)으로 저장하기로 해, 그 규칙을 펼치는 파이썬 라이브러리를 두 노드에 까는 role 변경을 만들었다. 장부의 새 코드가 올라가기 전에 깔려 있어야 새 코드가 스모크 시험에서 떨어지지 않는다. 전날의 래퍼 수정과 함께 두 노드에 적용했고, PATH 가 빈 셸에서 두 도구가 실행되는 것과 라이브러리 import 를 확인했다.
- 메신저 슬래시 명령 목록이 한 달 가까이 갱신되지 않는 문제(대화와 알림에는 지장 없음)를 원인 조사 할 일로 장부에 넣었다.
- 디스크 온도 세션에 먼저 연락해 진행 상황과 필요한 것을 물었다. 받은 케이스 팬 패치는 해시 대조, 시험(98개 통과, 강제 종료와 watchdog 시나리오 포함), 플레이북 문법 검사를 거쳐 서명 묶음으로 적용했다. 적용 때 서비스가 다시 뜨면서 팬을 BIOS 자동으로 돌려놓은 기록이 남아, 실제 칩에서의 복귀 시험을 따로 하지 않아도 됐다.
- 오전에 장부 작업 세션이 캘린더 명령 계약의 예고를 보내와 파일로 남겼다. 같은 메시지에서 짚은 빈틈도 확인했다. 아침 브리핑 러너도 새 코드를 받기 전에 스모크 시험을 돌리는데, 러너 유닛에는 웹 앱 import 시험에 필요한 환경 변수가 없어 동기화 쪽이 거절한 코드를 러너가 받을 수 있었다. 러너 유닛에 한 줄을 더하는 커밋을 만들어 두었다(적용은 10-09).

## AI 활용

- Claude Code(Opus 5.5)로 진행했다. 장부 작업 세션, 디스크 온도 세션과 원격 제어 메시지로 패치 전달, 적용 시각, 확인 항목을 맞췄다. 서명은 사용자가 하고, push 는 서명과 내용이 검토한 커밋과 같은지 확인한 뒤 했다.
- 좋았던 점: 점검 결과에 래퍼 작업마다 53줄이 지워진다고 나온 것을, 점검 모드에서는 링크가 실제로 지워지지 않아 링크 너머의 원본과 비교한 결과라고 가려냈다. 실제 적용 뒤 원본이 남아 있는 것도 확인했다.
- 아쉬웠던 점: 서명된 커밋을 원격에 올리기 전에 점검을 부탁해, 적용 스크립트의 안전장치(로컬과 원격이 같을 때만 실행)에 한 번 막혔다. 대화가 압축된 직후 영어로 답한 것이 이 세션에서만 세 번째였다. 그때 만든 피드백 초안을 말하지 않고 대기열에 넣어 두어, 사용자가 물은 뒤에야 설명했다.
