### 야간 세션 — driftline M2 착수 (계획 수립 + 구현)

#### 작업

  - 니즈만 넣으면 게이지가 0으로 떨어질 뿐이라 **충족 수단이 필요**한데 물자
    카탈로그는 M3다 → 배 위 **비품(fixture) 레이어**(침상·화장실·세면대·물통·
    배급통·신선식, 회 단위 `stock`)를 M2의 임시 형태로 도입.
  - 설계 문서의 항해 특성(멀미·육지/바다 갈망)은 파도(M6)·육지(M7)가 없으면
    동작할 수 없다 → 효과 없는 `pending` 선언으로만 남기고, 지금 동작하는 특성
    8종(대식가·검약한 위장·얕은 잠/깊은 잠·근면·굼뜸·결벽·낙타 방광)을 따로 정의.
  - 기분은 파생값으로만 넣고 오락 니즈·정신적 파탄은 M3 이후로 연기.
  - 결정론 공백(니즈 감소율 환산, 경로탐색 타이브레이크, AI 무작위성 금지)을
    규칙으로 못박고 문서화.
- 구현(`driftline-core`):
  - `defs`: 니즈·특성·비품 정의와 튜닝 상수를 담은 **규칙 세트**. 월드 상태에 들어가
    세이브·상태 해시·멀티 핸드셰이크 대상이 되고, 같은 내용을 `data/defs/core.ron`에
    미러링(M11 모드 로더 자리, 통합 테스트로 동일성 고정).
  - `need`: 니즈 6종 게이지(허기·목마름·수면·씻기·배설·비타민 C), 괴혈병 단계,
    생명력·사망. 감소율은 "하루당 비율"로 저작해 tick당으로 환산.
  - `path`: 4방향 A*(정수 비용, 해치를 통한 수직 간선, 완전 타이브레이크) +
    무작위 갑판에서 BFS와 대조하는 프로퍼티 테스트.
  - `job`: 작업 종류(건조·청소)·우선순위와 **난수 없는** 행동 선택 규칙.
  - `systems`: 니즈 → 건강 → 행동 배정 → 이동 → 작업 순으로 고정한 tick 스케줄.
  - `ship`: 비품·오염(filth)·건조 지정 레이어, 선체 절개·갑판 확장 규칙.
  - 새 입력 명령(건조 지정/취소, 작업 우선순위)에 맞춰 월드·입력 로그 포맷 버전을
    2로 올리고 골든 해시를 전량 재기록.
- 시나리오: 기본 "표류자"를 **2층(선창 + 주갑판, 해치 연결)** 으로 확장하고 비품 배치.
- 클라이언트: 비품(재고 바)·오염·건조 지정(진행 바)·폰 니즈 바 렌더, 마우스로 타일
  지정하는 도구(갑판/격벽/해치/침상/해체/취소) 추가 — 클릭은 클라 상태가 아니라
  시뮬 입력 명령으로 들어간다. 서버는 해시 로그에 승무원 요약(생존·활동·평균 니즈) 추가.
- 검증: 픽스처 5개(빈 월드, 침로, 니즈 이틀, 건조, 굶주림 사망)로 골든 고정 +

  약 27만 tick/s) 통과.

#### 추가 정리 (같은 세션)

- 사용자 질문을 받아 두 가지를 문서 결정으로 못박음.
  - **선체 물리(부력·적재·무게중심·흘수·기울임)와 충돌 판정**이 로드맵 어디에도
    배정돼 있지 않던 구멍을 확인 → 선체 물리는 M6, 충돌은 폰↔타일(M2 완료)·
    배↔지형(M6)·배↔배(M9) 세 종류로 나눠 ROADMAP에 "마일스톤에 걸친 주제"로 기록.
  - **조타로 배가 돌 때 배 타일과 바다 격자의 각도가 어긋나는 문제**: 두 격자는 축척부터
    달라(배 타일 ≈1 m, 바다 셀 수백 m 이상) 정렬 대상이 아니며, 배의 로컬 그리드는
    시뮬레이션상 회전하지 않고 연속 회전은 렌더에만 존재하도록 결정. 두 좌표계의 접점은
    배↔지형(대표점 좌표 변환), 배↔배(조우 인스턴스에서 90° 스냅), 배↔항구(갱웨이를
    경로탐색 간선으로) 세 곳뿐임을 ARCHITECTURE.md에 기록.
- 설계 문서 목록과 맞추려고 "선호 수면 장소(선실/육지)" 특성 2종도 pending으로 선언
  (규칙 세트가 해시 대상이라 골든 해시 5개 재기록).

#### M1·M2 결과물 보존 후 main 되돌림 (재설계 결정)

- 구현된 M2를 실제로 돌려 본 뒤, **원하던 조작감과 지금까지의 계획이 다르다**고 판단해
  계획을 처음부터 다시 짜기로 했다. 원하는 방향은 (1) 조타를 세세하게 하며 암초 같은
  장애물을 직접 피해 나가는 조작, (2) 다른 배·지상과의 상호작용에서도 배의 방향을
  90도 단위가 아니라 훨씬 미세하게 다룰 수 있는 방식, (3) 배경 설정(세계관)의 존재.

  - M1·M2 전체(코드·리플레이 픽스처·문서·CI 이력, 커밋 16개)를
    `archive/m1-m2-old-plan` 브랜치로 원격에 푸시해 보존.
  - `main`을 설계 문서 세트만 있던 시점(커밋 3개, 코드 이전)으로 되돌리고 강제 푸시.
    이제 main은 설계 문서 12종 + 크레이트 골대 + CI 골대만 남은 상태다.
- 되돌린 것은 저장소의 진행 상태일 뿐이고, 그때 확인한 사실(결정론 하네스가 실제로
  6타깃에서 동작한다는 것, 니즈·경로탐색·건조가 어떤 모양이 되는지)은 재설계의 입력으로
  남는다. 특히 이번 방향 전환은 "배 로컬 격자는 회전하지 않고 접현 시 90도로 스냅한다"는
  기존 결정을 정면으로 바꾸는 것이라, 좌표계·충돌·항해 축척 설계를 새 계획의 1순위로 둔다.

### 별건 — server-automation: Ansible 컬렉션 자동 설치

#### 작업

- raspi에서 셀프 프로비저닝(`ansible-playbook site.yml --limit raspi -c local`)이
  `couldn't resolve module/action 'ansible.posix.authorized_key'`로 실패. 원인은
  컬렉션 누락이었는데, 단순 누락이 아니라 **ansible-core가 두 벌 깔려 있어서** 생긴
  문제였다. 패키지 매니저로 깐 `ansible`은 컬렉션이 번들돼 있지만 그 번들은 그 패키지의
  core에서만 보이고, 같은 노드에 uv로 따로 깐 ansible-core가 PATH를 선점하고 있었다.
  그 core에는 사용자 컬렉션 경로에 `community.general`만 있고 `ansible.posix`가 없었다.
- 즉시 조치로 `ansible-galaxy collection install -r requirements.yml`을 실행해 복구.
- 재발 방지를 `roles/agentic_coding`에 넣었다: 저장소의 `requirements.yml`을 노드로
  복사한 뒤 사용자 컬렉션 경로에 galaxy로 설치하는 태스크 3개. 사용자 컬렉션 경로는 어느
  core를 쓰든 공통으로 읽히므로 위 충돌과 무관하게 동작한다.
  - `~/.ansible` 디렉터리는 존재만 보장하고 **mode는 지정하지 않았다** — 그 아래에 실행
    중 모듈 페이로드가 놓이는 `tmp/`가 있어서, 이미 있는 디렉터리의 권한을 role이 임의로
    넓히지 않게 하기 위함.
  - galaxy 출력에 "was installed successfully"가 있을 때만 changed로 잡아 재실행 시 멱등.
- 검증: 플레이북 syntax-check 통과, 새 태스크 3개만 떼어낸 검증용 플레이북을 localhost에
  두 번 실행해 1회차 changed=2 / 2회차 changed=0(멱등) 확인, 실행 전후 `~/.ansible` 권한
  불변 확인.
- README와 노드용 CLAUDE.md 템플릿에 "컬렉션 수동 설치는 컨트롤 노드에서만 필요, 코딩
  노드는 role이 자동으로 깐다"와 문제 시 복구 명령을 명시. 커밋 후 원격 master에 푸시.
