*(같은 날 - 키링 USB 정리와 예비 컨트롤 노드 설치)*

## 작업

- 두 번째 토큰과 같은 키링에 단 USB 메모리 두 개의 내용을 읽기만으로 분석함. 작은 쪽에는 옛 설치 USB 와 설치에 실패한 기록이 남아 있었고, 그 기록에 계정 정보가 들어 있어 지우기를 권함. 큰 쪽은 비어 있었음
- 작은 USB 는 사용자 승인으로 복구용 Arch 설치 USB 로 다시 만듦. ISO 는 체크섬과 릴리스 서명으로 확인했고, 쓰기 스크립트는 사용자가 sudo 로 돌림. 쓴 뒤 다시 읽어 대조했고 ISO 안의 체크섬도 통과함
- 큰 USB 는 사용자 제안으로 예비 컨트롤 노드로 만듦. 컨트롤 노드 카드가 첫 번째 토큰과 같은 키링에 있어, 그 키링을 통째로 잃어도 다른 키링만으로 부팅해 인증서를 발급하고 잃은 토큰을 폐기할 수 있게 하려는 것
  - 사용자 결정: 두 번째 토큰 하나로도 모든 작업이 되게 함, Windows 데스크톱에서도 두 번째 토큰을 쓰게 함, 보관 파티션도 넣음, 디스크는 비밀번호와 두 토큰 모두로 열리게 함, 데스크톱 환경도 카드와 같게 넣음
  - 세션이 USB 메모리라 카드보다 느릴 것이라고 하자, 사용자가 빠르면 빨랐지 느리지는 않을 것이라고 되물어 두 매체를 직접 I/O 로 재 봄. USB 가 순차 읽기 약 2배, 작은 동기 쓰기 약 10배 빨라 세션이 앞선 말을 철회함
  - 위 서버 설정 저장소 절의 인증서와 FIDO2 키 스크립트의 토큰 고르기 변경은 이 작업에서 나왔음. 설정 저장소(설치 스크립트)에는 예비 노드용 기기 설정과, 컨트롤 노드 설치가 그 기기의 토큰을 쓰게 하는 변경을 넣음
  - 서버 설정 세션의 적용이 끝난 뒤 사용자가 서명함. 세션이 서명과 원래 커밋과 내용이 같은지 확인하고 서버 설정 저장소를 push 했고, 설정 저장소는 사용자가 push 함
  - 설치 도중 사용자가 기기 이름을 바꾸기로 해, 이름 변경 커밋을 만들고 사용자가 서명하고 push 함
  - 설치는 사용자가 돌림(약 1시간). 세션이 파티션 구성, 보관 파티션의 UUID 가 카드와 겹치지 않게 바뀐 것, 호스트 이름, 카드와의 패키지 차이(카드에만 있는 85개는 일부러 뺀 게임 패키지 등으로 모두 설명됨)를 확인함
  - 토큰 등록 중 토큰을 뽑다가 USB 가 빠짐. 등록은 이미 끝나 있었고, 세션이 복구 단계를 스크립트에 더해 낡은 장치 연결을 걷어 내고 파일 시스템(데이터 체크섬 포함)과 부트 파티션을 검사함. 부트 파티션의 dirty 표시 하나만 정리했고 손상은 없었음. 마지막에 두 파티션이 비밀번호, 두 토큰 모두로 열리는 것을 사용자가 확인함
  - 파일 관리자에서도 FIDO2 토큰으로 열 수 있는지 물었으나, 데스크톱의 디스크 관리 서비스가 토큰을 쓰지 않아 접음
- 남은 것: 예비 노드 첫 부팅과 컨트롤 노드 설정, Windows 데스크톱에 두 번째 토큰의 키 핸들 옮기기. 자주 켜지 않는 기기라 한 달에 한 번 켜서 업데이트하라는 안내를 기기 설정 주석에 적음
